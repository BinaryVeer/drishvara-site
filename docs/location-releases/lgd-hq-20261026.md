This release qualifies 2,542 additional headquarters reference points: 275 district headquarters (official coordinate source epoch 2017) and 2,267 subdistrict headquarters (2022). Existing five approved places remain unchanged. The expected active total is 2,547.

The user explicitly accepted older official coordinate references on 26 October 2026, with correction on new data or reported errors. This is an acceptance of the official reference basis, not a claim that the coordinates were resurveyed in 2026. Typed LGD identities and hierarchy were reconciled to nine supplied October 2026 exports. All 2,542 points agreed with Asia/Kolkata in the full TBB 2026e polygon crosscheck; 10,168 internal calculation cases executed. These checks do not constitute independent astronomical benchmarking or historical timezone certification.

The compressed, UTF-8 JSON release is at `data/location-releases/lgd-hq-20261026.json.gz`. Its uncompressed SHA-256 is recorded in the adjacent review JSON. Every record carries its administrative type, LGD code, state, district, coordinates, IANA timezone, official source URL, original epoch, acceptance basis and correction policy. Headquarters points represent the administrative headquarters, not a district centroid or an exact birth address. Bedauliya village and Bhawanathpur Township are not silently substituted with Kutumba or Bhawnathpur subdistrict headquarters; their separate unresolved identities remain outside this batch.

## Deployment

1. Deploy the updated `calculate-panchang` Edge Function using the existing authenticated Supabase project workflow. Its POST `{ "action": "locations" }` must return catalog version `20261026` and the original five records before database activation.
2. Run `node scripts/activate-lgd-headquarters.mjs` for the offline payload preflight.
3. With `SUPABASE_DB_URL` supplied securely in the operator's environment, run `node scripts/activate-lgd-headquarters.mjs --apply`. This first checks the deployed catalog version, then performs one database transaction. It requires exactly one active source manifest, the original five-place count, a matching privacy-preserving runtime, and no identity collisions. It preserves the source release ID, existing records, daily calendar, festivals and Word systems. It inserts 2,542 rows, updates the location extension metadata/count and records the previous manifest in a private activation audit table. Any failure rolls back the transaction.
4. Run `node scripts/readback-lgd-headquarters.mjs`. It compares all additions against the public server catalog and exercises representative named calculations. Then verify Panchang and Star Reflection in a real browser with date/time inputs, keyboard and mobile layouts.

Alternatively, `--write-sql /absolute/path/activation.sql` generates the same transaction for review/execution in the established database administration workflow. Do not commit credentials or generated connection strings.

The frontend loads only the server-active catalog and shares it across its existing controllers and typeahead. If the backend does not support the catalog action or is unavailable, it retains the unchanged five-record projection. The old name-only pending discovery bank is no longer offered in live search. Expanded locations are never silently converted to coordinate-mode requests to bypass server approval. The catalog supports pagination beyond Supabase's default row cap, and ambiguous free-text names require explicit selection.

## Corrections and rollback

On a credible conflict, suspend the affected record's public-selection/computation/public-output flags before publishing a correction, then review its typed LGD identity and official geographic evidence. Preserve the old evidence and correction reason. Newly available official data triggers review; retrieval date does not replace source epoch. The server refuses suspended locations and omits them from its public catalog.

`node scripts/rollback-lgd-headquarters.mjs` performs an offline dry run; `--apply` uses the securely supplied database URL. The activation audit stores the previous manifest and batch hash privately. Rollback must remove only this batch's exact IDs under the recorded source release, and restore its saved manifest only if the current location extension still matches this batch; reconcile any later changes first. Do not delete the original five places or unrelated releases. Automatic replay/overwrite of an activated batch is rejected.

## Production activation — 27 October 2026

The function was deployed as version 7, preserving its previous JWT setting, import map and unchanged astronomical runtime. Activation completed at 2026-10-27T04:10:25.581562Z. The active catalog contains 2,547 places; 384 daily records and 114 observances remain unchanged.

The management API rejected the initial all-in-one migration before execution because it exceeded its body-size limit. The approved payload was then staged in transactional chunks in the non-exposed, RLS-protected `drishvara_location_staging.headquarters_20261027` table. Migrations `stage_lgd_headquarters_release_20261027` and `activate_staged_lgd_headquarters_20261027` record the schema and final atomic activation. The final transaction checked 2,542 unique staged identities and source-payload hashes, retained the original five, and saved the previous manifest in the private activation audit. Partially staged records never entered public selection.

Live readback matched all 2,542 additions and nineteen representative named calculations passed. Coordinate comparisons allow up to 1e-12 degrees for PostgreSQL JSON float serialization; original source coordinates remain intact. A real browser verified Kutumba Panchang selection/calculation for 27 October 2026 and Star Reflection using synthetic 01/01/2000 input with unknown time. Reflection retained its day-context limitation and displayed LGD 1484 with the 2022 source basis.

The language presentation layer now reads the controller's selected record rather than relying on the removed fixed-city buttons, so localization cannot incorrectly clear the visible birthplace summary.

Security advisors flagged RLS-without-policy information for the private staging/audit tables. This is intentional deny-by-default behavior with client privileges revoked; no allow policy was added. See [Supabase's advisory](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). Unrelated project advisories were not changed.
